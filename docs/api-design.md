# API design (v1)

Design contract for the REST API. The final reference will be generated with OpenAPI/Swagger once the code exists; this document defines what will be built.

## Conventions

- Base path: `/api/v1`
- Format: JSON (`application/json`)
- Authentication: `Authorization: Bearer <access_token>`
- Ids: UUIDs
- Money: integer cents plus currency (`"priceCents": 19990, "currency": "BRL"`)
- Dates: ISO 8601, UTC
- Pagination: `?page=0&size=20&sort=price,asc`, response contains `content`, `page`, `size`, `totalElements`, `totalPages`

## Access levels

| Level | Meaning |
|---|---|
| Public | No login required |
| Customer | Logged in user (role `CUSTOMER`) |
| Admin | Logged in user with role `ADMIN` |
| Signed | Not a user: request signed by Stripe (webhook) |

## Identity

| Method | Path | Access | Description |
|---|---|---|---|
| POST | `/auth/register` | Public | Create account (email, password) |
| POST | `/auth/login` | Public | Returns a short-lived access token (JWT) and sets a refresh token in an `HttpOnly` cookie |
| POST | `/auth/refresh` | Public (cookie) | Issues a new access token |
| POST | `/auth/logout` | Customer | Invalidates the refresh token |
| GET | `/users/me` | Customer | Current user profile |

Notes:

- Passwords are hashed (BCrypt or Argon2). Never returned, never logged.
- Login errors do not reveal whether the email exists.
- Rate limiting on `/auth/*` is planned as a later improvement.

## Catalog

| Method | Path | Access | Description |
|---|---|---|---|
| GET | `/products` | Public | List with filters: `search`, `category`, `minPrice`, `maxPrice`, plus pagination and sorting |
| GET | `/products/{id}` | Public | Product details, including whether it is in stock |
| GET | `/categories` | Public | List categories |
| POST | `/admin/products` | Admin | Create product |
| PUT | `/admin/products/{id}` | Admin | Update product |
| DELETE | `/admin/products/{id}` | Admin | Deactivate product (soft delete: `active = false`) |
| PUT | `/admin/products/{id}/inventory` | Admin | Set available quantity |

Products are deactivated, not deleted, so past orders keep their history.

## Cart

| Method | Path | Access | Description |
|---|---|---|---|
| GET | `/cart` | Customer | Current cart with totals |
| POST | `/cart/items` | Customer | Add item (`productId`, `quantity`) |
| PATCH | `/cart/items/{itemId}` | Customer | Change quantity |
| DELETE | `/cart/items/{itemId}` | Customer | Remove item |
| DELETE | `/cart` | Customer | Empty the cart |

The cart does not reserve stock. Reservation happens only when the order is created.

## Orders and payments

| Method | Path | Access | Description |
|---|---|---|---|
| POST | `/orders` | Customer | Create an order from the cart, reserve stock, create the first payment. Returns the order and `checkoutUrl` (Stripe) |
| GET | `/orders` | Customer | List own orders |
| GET | `/orders/{id}` | Customer | Order details (own orders only) |
| POST | `/orders/{id}/payments` | Customer | New payment attempt for an order still in `CREATED` |
| POST | `/orders/{id}/cancel` | Customer | Cancel an order in `CREATED` and release the reservation |
| GET | `/admin/orders` | Admin | List all orders, filter by status |
| PATCH | `/admin/orders/{id}/status` | Admin | Move a paid order to `SHIPPED` or `DELIVERED` |

### Creating an order

Request header: `Idempotency-Key: <uuid generated by the client>`

If the customer double-clicks "Pay" or the network retries the request, the same key returns the same order instead of creating a second one.

Response (`201 Created`):

```json
{
  "orderId": "0b8f6c1e-...",
  "status": "CREATED",
  "totalCents": 24990,
  "currency": "BRL",
  "checkoutUrl": "https://checkout.stripe.com/..."
}
```

Steps, all inside one database transaction until the Stripe call:

1. Validate the cart (not empty, products active).
2. Reserve stock for every item. If any item has insufficient stock, nothing is reserved and the API returns `409 Conflict`.
3. Create the order and the order items with price snapshots.
4. Create the Stripe Checkout Session and the `PENDING` payment.

### Order status rules

```
CREATED -> PAID -> SHIPPED -> DELIVERED
   |
   +--> CANCELED   (from CREATED or PAID)
```

Invalid transitions return `409 Conflict`.

## Stripe webhook

| Method | Path | Access | Description |
|---|---|---|---|
| POST | `/webhooks/stripe` | Signed | Receives events from Stripe |

Processing rules:

1. Read the **raw** request body and verify the `Stripe-Signature` header with the webhook secret. Invalid signature: `400`, nothing is processed.
2. Look up the event id in `STRIPE_EVENTS`. If it already exists, return `200` and do nothing (idempotency).
3. Handle the event inside a transaction and store the event id in the same transaction.

| Stripe event | Effect |
|---|---|
| `checkout.session.completed` | Payment `SUCCEEDED`, order `PAID`, reservation confirmed |
| `checkout.session.expired` | Payment `FAILED`, reservation released if the order is not paid |

Always answer `2xx` quickly, so Stripe does not retry unnecessarily. Order status changes come only from webhooks, never from the browser returning to the site.

A scheduled job also releases reservations of orders that stayed in `CREATED` past the Checkout Session expiration time, as a safety net.

## Error format

All errors use the same structure:

```json
{
  "status": 409,
  "error": "INSUFFICIENT_STOCK",
  "message": "Not enough stock for product 'Winter Coat'.",
  "timestamp": "2026-10-08T14:32:10Z",
  "path": "/api/v1/orders"
}
```

| Status | When |
|---|---|
| 400 | Invalid input (validation) |
| 401 | Not authenticated or token expired |
| 403 | Authenticated but not allowed (wrong role, or someone else's order) |
| 404 | Resource not found |
| 409 | Conflict with current state (insufficient stock, invalid status transition) |
| 500 | Unexpected error (details never exposed to the client) |

## Security checklist

- Every endpoint is protected by default; public ones are listed explicitly.
- Customers can only read their own orders and cart (ownership check in the use case, not only in the controller).
- Input validation on every request body.
- CORS restricted to the frontend origin.
- Secrets (JWT key, Stripe keys, webhook secret) only in environment variables, never in the repository.
- Stripe is used in test mode only.
